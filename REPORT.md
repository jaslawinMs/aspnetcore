# Measured AutoPerf findings: classification and artifact map

**Snapshot: 18 November 2026 (UTC). Nothing here is a shipped improvement or a merge approval.**

The campaign has finalized **118 of 358 retained findings**, producing **72 fork-only
draft PRs**. This report catalogs **70 proposals with a scoped measured benefit**.
No-gain, rejected, duplicate and inconclusive recommendations are omitted; the
[complete inventory](findings.md) and [evaluation index](README.md#evaluations)
remain available. The inventory and dispositions have not been rewritten for this report.

**Where David's list is:** [David Fowler's performance-effort index,
dotnet/aspnetcore#70219](https://github.com/dotnet/aspnetcore/issues/70219).
His [OutputCache PR](https://github.com/dotnet/aspnetcore/pull/70199) and
[RenderBatchWriter PR](https://github.com/dotnet/aspnetcore/pull/70125) are useful
examples: explain the unnecessary work, show before/after time and allocation,
state the tested boundary, and keep costs visible. This report follows that
presentation, with an additional map connecting our separately published artifacts.
Their measurements are not our measurements.

## Reading the classifications

| Review class | Meaning |
|---|---|
| **Large local result** | Approximately 50% or greater time/allocation reductions on the specified target, without the material target-input trade-offs that put other large numbers in the conditional class. Not an application-wide impact rating. |
| **Focused efficiency** | A smaller CPU improvement or a demonstrated allocation reduction. Often the sensible "good to have" category; allocation-only changes are not advertised as speedups. |
| **Workload-dependent trade-off** | A demonstrated benefit for a particular input shape, cardinality, configuration or warmed state, accompanied by costs or important applicability limits. Requires workload fit, not a blanket recommendation. |
| **Correctness / resource lifetime** | A real original failure or retained-resource problem is reproduced and corrected. Distinct from preservation tests that already pass before an optimization. |

The **technique** is named separately in each row: direct runtime/BCL use,
allocation/buffer shaping, data-structure fit, metadata reuse/removal or deferred
diagnostics. A newer API or shorter syntax is a mechanism, not evidence of improvement.

**Numbers:** percentages mean less elapsed time or fewer allocated bytes for the
named boundary, not more application throughput. "Pairs" below means comparisons
of the **selected final implementation**; rejected strategies and failed attempts
still consume the campaign's three-comparison limit and remain in the full record.
One pair is an observation, not three repetitions. Do not add gains from independent
branches or average results from different implementations.

**Artifact columns:** `PR` opens the code proposal, `issue` its fork tracking issue,
`BDN` the actual project, `A/B` the full comparison, `record` the case report with
raw exports and provenance, and `tests` the recorded local checks/commands.
F116 and F118 have no separate fork tracking issues recorded; those cells say so.
F107 also links its separate convention proposal.

## Why the logging guards can save work without skipping the real operation

**They do not do the same CPU work. They deliberately omit diagnostic-only work
when the event would be filtered. The required operation still runs.**

C# evaluates call arguments before entering a generated logging method. An
internal generated `IsEnabled` check is too late to prevent the caller's
`string.Join`, enumeration or enum/text formatting. The intended transformation is:

```csharp
// Before: formatting runs even when the generated logging method rejects the event.
LogDiagnostic(logger, FormatDiagnostic());

// After: only the diagnostic formatting and event are conditional.
if (logger.IsEnabled(theEventsExistingLevel))
{
    LogDiagnostic(logger, FormatDiagnostic());
}

ProcessTheActualUpdate(); // Remains outside the guard.
```

This is explanatory pseudocode, not a new patch.

For **F051/F052**, the actual level is **Debug**. The final source moves the check
to the caller and sets `SkipEnabledCheck = true` on the one generated helper,
so it does not add a redundant inner check. F051 keeps `updateIndex++` outside
the guard: disabled logging cannot stop the stream index advancing.
The [F051 patch](F051/source.patch) and [F052 patch](F052/source.patch) make the
small guarded regions explicit. Their producer-driven tests consume real streamed
updates and compare actual blocks, lifecycle, history and enabled event fields.

For **F053/F054**, the real handler/catch-up call and its state transition remain
outside the guard. The generated shared helper **still has its own check**, so
an enabled diagnostic can incur an extra `IsEnabled` call. That is not equivalent
check-count behavior to F051/F052, and enabled costs must stay visible.
The [F053 patch](F053/source.patch) and [F054 patch](F054/source.patch) establish
this boundary. Recorded tests validate enabled/disabled states and real processing;
this report does **not** claim identical observations for every custom logger whose
filter changes between checks. Nor does an observed 24-byte diagnostic interval
prove that every enum `ToString()` creates a fresh string.

For **F055/F056**, the actual existing event is **Information, not Error**.
The real handlers/evaluator have already produced the failure and original
reason/requirement objects. Only diagnostic joining/stringification is deferred;
the failure result and object identities are still returned. Each branch has
one outer Information check and the private generated event skips its own check:
[F055 final source](F055/source-after-2.cs), [F056 final source](F056/source-after.cs).
These proposals intentionally stop evaluating diagnostic formatters/enumerables
when filtered; they do not promise to preserve arbitrary side effects of omitted
diagnostic formatting. The substantial enabled-path costs are why these two are
classified as **workload-dependent trade-offs**, not universal wins.

## Other non-obvious equivalence and scope points

**TempData is not an ordinary interchangeable Dictionary API (F039/F040).**
Public TempData `TryGetValue` consumes a key for later Save semantics. The proposals
instead use the private `Data` dictionary. Contains remains non-consuming;
Remove still calls the same final `Remove(key)` and returns its result, including
when value equality reenters and changes the dictionary. Replacing the calls with
the public method, or skipping the final removal, would not be the same change.
See the [Contains](F039/validation-commands.md) and
[Remove](F040/validation-commands.md) preservation records.

**A completed-result optimization is not removal of a required synchronous wait
(F092/F094).** Only `IsCompletedSuccessfully` takes the direct result. Pending,
faulted or canceled operations retain their original synchronous wait/exception
path. F094's public async method still returns a Task. The benefit is the wrapper
allocation avoided for a particular completed synchronous call, not a claim that
blocking was fixed or all rendering/reads became allocation-free.

**A collection's shape and comparer are part of the decision (F010/F028/F059/F131/F241).**
The branches preserve custom/derived providers and comparers rather than assuming
every interface behaves like a standard Dictionary/HashSet. F131 is a useful
data-structure-fit example: the measured final ordinary Dictionary index suits
this fixed 25-entry read-many map better than the rejected FrozenDictionary
prototype; the original immutable map remains for its other purposes.
This is not evidence to replace all immutable or frozen collections.

**Pooling is not zero-copy or lower retained memory (F025/F027/F111/F112/F118).**
The independently owned result is still copied where required. Warm rentals
can reduce allocated B/op while the pool retains arrays/builders. Cold misses,
oversized inputs and concurrency can change the trade-off; the tables do not
turn warm allocation measurements into resident-memory claims.

**Removing a UTF16 bridge is not network streaming (F018/F081/F082).**
The actual HTTP completion mode still buffers responses. Charset, BOM, invalid
UTF8 replacement and awaited document lifetime explain the guards and fallbacks.
Direct strict UTF8 parsing for every response would change behavior; the
malformed/other-encoding costs remain in the comparisons.

**F107 needs convention review, not just passing tests.** Its empty contents still
satisfy `IReadOnlyList<IFormFile>`, but concrete type, identity and mutable-downcast
behavior change. [jaslawinMs/aspnetcore#28](https://github.com/jaslawinMs/aspnetcore/issues/28)
is open with `api-suggestion`/`api-proposal`, **without `api-approved`** at this
snapshot. The implementation draft and compatibility/resource tests are not
approval to include that final convention in an RTM release.

## Validation, exclusions and reproducibility limits

Across **all 72 published drafts**, each has a committed BenchmarkDotNet project.
**60 have test-file changes; 12 do not** and instead record existing-test coverage.
Most projects/raw exports deliberately live on `autoperf-results`, not in the
shipping PR diff. New optimization tests usually preserve ordering, exceptions,
state, identity or resource behavior; they do not mean the original feature lacked
tests or had a functional bug.

**All 72 are currently open drafts with zero visible GitHub CI checks.**
The `tests` links are local execution evidence, **not green GitHub CI**.
Historical PR checklist boxes are inconsistent, so this report does not infer
test execution from a checkbox. It summarizes the published records and current
PR identities; it does not claim that all historical suites were rerun for this
documentation task or that the proposals are ready to merge upstream.

Two additional draft studies are intentionally not recommendation rows:
[F033](F033/README.md) has a mixed declared completed-callback primary; a favorable
supporting no-callback profile is not promoted into its primary.
[F181](F181/README.md) has mostly mixed/worse complete-builder results and only
three repeatedly favorable successful-membership shapes; it does not support a
general DFA-construction recommendation. This report's selection does not change
their archived evidence or historical draft dispositions. The 19 no-gain,
21 rejected and 6 duplicate finalized cases are also not recommendation rows.

The evidence snapshot is results commit
[`c6156fef6c61f9938241703e21620a25fd006484`](https://github.com/jaslawinMs/aspnetcore/commit/c6156fef6c61f9938241703e21620a25fd006484).

`37e809ead5824bc753a1c3d56f11615bdb1296c5`, with per-case scoped current-default
